# CP06.3 — صيغة النسخة الاحتياطية وإصداراتها

الكود: `mobile/src/backup.ts` (الصيغة) و`mobile/src/worker.ts` (الإنشاء والاستعادة) و`mobile/src/client.ts` (الكتابة على القرص وقراءة الشرائح).

## الإصدارات المدعومة

| الصيغة | تُنشئها | تُقرأ في 3.0.0-cp06.3 | ملاحظة |
|---|---|---|---|
| `MHBAK1` | 3.0.0-cp06، 3.0.0-cp06.2 | **نعم** | تُفك دفعة واحدة (صيغتها بوسم GCM واحد للملف كله)، ثم تُكتب في الخانة الاحتياطية وتُفحص بنفس الطريقة. الذاكرة ≈ ضعف حجم القاعدة **لهذه الملفات القديمة فقط** |
| `MHBAK2` | 3.0.0-cp06.3 فأحدث | **نعم** | بث كامل، ذاكرة محدودة |
| `MHBAK2` في إصدار قديم | — | **لا** | الإصدارات السابقة ترفضها برسالة «الملف ليس نسخة احتياطية…» — لا ضرر، لكن لا رجوع لإصدار أقدم بنسخة جديدة |

## بنية MHBAK2

```
"MHBAK2\n"
<سطر رأس JSON>\n            format, app, created_at, schema[], counts{products,images,users},
                             page_size, page_count, chunk_bytes, kdf{PBKDF2-SHA256, iter 310000, salt},
                             cipher{AES-256-GCM-CHUNKED, iv_prefix (8 بايت)}  — لا أسرار في الرأس
إطار*                        u32BE(طول) + AES-256-GCM( نوع(1 بايت) + حمولة )
                             iv  = iv_prefix + u32BE(رقم الإطار)
                             aad = SHA-256(سطر الرأس) + u32BE(رقم الإطار)
                             نوع 0 = بيانات: صفحات SQLite متتالية (≤ 1 MiB)
إطار النهاية                 نوع 1 = JSON { frames, plain_size, plain_sha256 }
```

| الهجوم/العطل | يُكتشف لأن | مختبر |
|---|---|---|
| كلمة مرور خاطئة | فشل فك أول إطار | ✔ |
| تعديل بايت | وسم GCM للإطار | ✔ |
| حذف آخر الملف (اقتطاع) | لا يوجد إطار نهاية | ✔ |
| تبديل ترتيب الإطارات | رقم الإطار داخل IV وAAD | ✔ |
| تعديل الرأس (مثل الأعداد) | تجزئة الرأس داخل AAD لكل إطار | ✔ |
| بايتات زائدة بعد النهاية | تُرفض صراحة | ✔ |
| تلف داخلي في SQLite | `integrity_check` على النسخة المستعادة قبل التبديل | ✔ |
| نسخة من إصدار أحدث | قائمة الترحيلات في الرأس | ✔ (موروث) |

## الإنشاء (ذاكرة محدودة)
1. قفل في العامل: لا يُنفّذ أي طلب آخر أثناء النسخ (لا كتابة داخل معاملة القراءة).
2. `PRAGMA integrity_check` ثم `BEGIN` (لقطة متسقة).
3. قراءة الصفحات من `sqlite_dbpage` على دفعات ~1 MiB ← تشفير ← إرسال للواجهة ← انتظار تأكيد ← الدفعة التالية.
4. أندرويد: كل دفعة تُضاف إلى الملف (`Filesystem.appendFile`) ثم تفتح شاشة المشاركة. المتصفح المكتبي: تُجمع الدفعات وتُنزّل.
**لم يعد `sqlite3_js_db_export` مستخدمًا** (كان ينسخ القاعدة كاملة في الذاكرة).

## الاستعادة (لا تمس البيانات الحالية قبل النجاح)
1. العامل يطلب شرائح من الملف المختار (`File.slice`) واحدة تلو الأخرى.
2. كل إطار يُفك ويُتحقق منه **قبل** كتابته في **الخانة غير النشطة** (`/makeup-house.db` أو `/makeup-house-b.db`) عبر `importDb` المجزأ.
3. فحص النسخة في تلك الخانة: السلامة، الأعداد مقابل الرأس، وجود حساب.
4. التحقق فقط (dry): تُحذف النسخة المؤقتة.
5. التبديل: مؤشر صغير في `/slot.db` يشير للخانة الجديدة ← فتح + ترحيل + فحص ← حذف الخانة القديمة. أي فشل بعد التبديل يعيد المؤشر للقاعدة السابقة (لم تُلمس).
- التثبيتات القائمة: لا مؤشر ← الخانة A = اسم الملف الأصلي، فلا شيء يتحرك عند التحديث.
- المساحة: أثناء الاستعادة يلزم مكان لنسختين على القرص مؤقتًا (لا في الذاكرة).
