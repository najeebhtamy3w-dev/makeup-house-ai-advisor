# تجربة Planner مختصر — النتيجة: لا تحسن دلالي مثبت

التجربة معزولة؛ لم يُعدّل Prompt الإنتاج أو Runtime أو Orchestrator. النموذج Qwen3.5-2B Q4_K_M الحقيقي على Host، وبنفس Grammar الكامل والقيود وقواعد التطبيق في الجانبين. لا Holdout ولا إجابات محفوظة ولا اختيار أدوات نيابة عن النموذج.

## الفرضية والبروتوكول

بعد فشل خطط أسئلة جديدة في المسار الرئيسي، اختُبرت فرضية أن كثافة التعليمات (~633 Input في مثال القدرات السابق) تُضعف فهم2B. كُتب System عربي أقصر، **207 Token** مقاسة بـTokenizer الحقيقي في تحميل Vocabulary-only؛ واحتفظ بعقد Plan الكامل والسلامة وأسماء الحقول والحدود. لا أمثلة أجوبة ولا نص أسئلة الاختبار داخل أي System.

ثُبتت ثلاث حالات ومراجعها **قبل التوليد** في `cases-and-references-before-evaluation.json`:

1. سؤال جديد عن دور المستشار وحدود مساعدته.
2. سؤال شرطي عن نوع المساعدة الممكنة عند تقديم مكونات العبوة، لا قائمة مكونات فعلية تحتاج استيضاحًا.
3. لمعان الجبهة وتقشر حول الفم وتهيج العطر، مع طلب تفسير تجميلي وخطوة أولى. سُمح مسبقًا consultation أو clarify في مرجع هذه الحالة لأن استيضاحًا مناسبًا قد يكون مشروعًا؛ تقاس ملاءمة السؤال والسياق منفصلًا.

لكل حالة نُفذ Baseline ثم Concise، مع نفس ذاكرة البداية وقائمة الأدوات والـGrammar وmax_tokens. يعيد Runtime ضبط السياق بين الطلبات، فتُختبر رسائل مستقلة لا استمرار محادثة غير متاح. هذه مقارنة تطويرية من6طلبات، لا عينة قبول شاملة.

كل الطلبات أعادت JSON صالحًا وانتهت stop، لكن **هذا لم يصبح فهمًا صحيحًا**:

- في السؤالين الأول والثاني لم يحدد أي جانب intent=capabilities أو يستدعِ get_system_capabilities.
- بقيت concerns فارغة في سؤال لمعان الجبهة والتقشر والعطر، ولم تُستدع أدوات العلم/التخصص.
- Baseline سأل عن نوع البشرة **والشعر** رغم أن السؤال الثالث يصف الوجه فقط.
- Concise سأل المستخدم: «ما هو دورك في تقديم تفسير تجميلي…؟»، فبدل أدوار المستخدم والمساعد وأعاد صياغة الطلب كسؤال غير مناسب.
- اختار Concise `correction=true` في الحالات الثلاث، رغم عدم وجود تصحيح سابق؛ Baseline أبقاه false.

ملاحظة نزاهة مهمة: يسجل الحقل الآلي `intent_expected=true` في الحالة الثالثة لأن المرجع **المسبق** سمح clarify. لا يُفسر هذا كنجاح وظيفي؛ ملاءمة الاستيضاح واستخراج الحقائق والأداة لم تتحقق. لم نغيّر المرجع بعد النتائج لإظهار نجاح أو إخفاء فشل.

## الاستنتاج

انخفض Input وTTFT والزمن الوصفي، لكن **لم يثبت تحسن في الفهم أو اختيار الأداة**. في هذه العينة بلغ متوسط TTFT تقريبًا9.306s مقابل5.482s، ومتوسط Generation28.196s مقابل19.934s. هذه أوصاف Host في بيئة تطوير مشتركة، لا تقديرات هاتف أو p95 قبول، ولا مكسب ذكاء.

**التوصية: عدم اعتماد هذا Prompt المختصر في الإنتاج بناءً على هذه التجربة.** تقصير التعليمات وحده لم يعالج المشكلة، وصحة JSON أو زمن أسرع لا يبرران تبديل حالة الفشل إلى نجاح. كذلك لا تعمم ستة طلبات الحكم على كل Prompt أو كل عائلة نموذج؛ لكنها تمنع ادعاء تحسن هذا المرشح دون دليل جديد.

أي تجربة لاحقة يجب أن تغيّر فرضية ذات معنى وتحفظ المقارنة، مثل تخفيف عبء التخطيط المعقد أو اختبار مكوّن NLU/نموذج آخر، مع بقاء الاختيار التوليدي والحوكمة قابلين للقياس. لا أضيف تلك التغييرات تلقائيًا ولا أبرمج أجوبة هذه الأسئلة في التطبيق.

## الأدلة

- `concise-system.txt` و`token_count.cpp`: التعليمات المختبرة وأداة عدّ Tokens الفعلية.
- `results/metadata.json`: System القديم والجديد وبصمات النموذج والثنائي وحدود التجربة.
- `results/cases-and-references-before-evaluation.json`: الحالات والمراجع المجمدة قبل التنفيذ.
- `results/raw-responses.jsonl`: المدخلات والمخرجات والقياسات الستة كاملة.
- `results/summary.json`: ملاحظات مفصلة، دون نسب جودة عامة ملفقة.
- `probe_concise.py`: إعادة التنفيذ؛ لا يحتاج نموذجًا جديدًا أو تعديل التطبيق.
